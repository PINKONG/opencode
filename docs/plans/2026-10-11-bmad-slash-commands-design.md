# BMAD 技能斜杠命令兼容设计（评审稿）

状态：设计评审通过，功能已实施，macOS 人工验证通过，待 Windows 构建验证。它补充 [BMAD 内嵌设计](2026-10-10-bmad-integration.md)，不改变技能安装目录、uv、版本更新和文件所有权策略。

## 目标与边界

让老用户在执行 `/bmad-init` 后，能在 CLI 和 V2/Web 中通过 `/bmad-agent-analyst`、`/bmad-prd` 等斜杠入口找到并运行**当前实际发现的** BMAD 技能，同时仍能从 `/skills` 找到它们。入口是技能的另一种调用方式，不是第二份 BMAD 内容，也不是新的安装产物。

- 候选名称仅为精确 `bmad` 或以 `bmad-` 开头的已发现技能；不根据历史命令表、vendor 目录名或 `_bmad/` 内容臆造命令。未安装、被移除或发现失败的技能不显示。非 BMAD 技能维持现有展示方式。
- `/bmad-init` 是现有初始化命令，不得被技能派生入口覆盖。已有同名用户/配置命令继续优先；也不得覆盖内置命令或 MCP 命令。一次补全中同名入口只出现一次，实际执行与显示选择同一个目标。
- `/bmad-help` 是 `/bmad` 的纯兼容别名：两者使用同一份当前 `bmad` 技能正文及相同的参数处理，不额外拼接“求助”提示词。只有发现 `bmad` 且不存在任何同名命令或技能时才提供。当前快照没有独立 `bmad-help` 技能，不复制或改写上游帮助正文。
- 不给所有技能开放斜杠补全，不生成项目级 `.opencode/commands/*.md`，不改 vendored `SKILL.md`，不把缺失的旧命令（例如未随当前模块安装的技能）伪装为可用。

V2 命令执行不展开 V1 的 `` !`shell` `` 模板语法；这是 V2 命令平台的既有能力边界，BMAD 技能正文不依赖该语法。本次兼容功能不扩大此能力范围。

## 已核实的现状

- V1 `packages/opencode/src/command/index.ts` 已把 `Skill.Service.all()` 的结果桥接为 `source: "skill"` 命令；配置和 MCP 命令先登记，技能遇到同名命令会跳过。CLI `footer.prompt.tsx` 接受手输的技能命令，`/skills` 单独列出技能，但普通 `/` 自动补全明确过滤 `source: "skill"`。
- Web 的斜杠候选来自 `sync().data.command`（`prompt-input.tsx` 与 `prompt-input-v2.tsx`）；提交路径根据同一列表判断命令。V1 数据来自 legacy `command.list()`；V2 数据来自 `/api/command` 的 `CommandV2.list()`。现有 Web 映射没有保留 V1 的 `source`，V2 `CommandV2.Info` 也没有 `source` 字段。因此 Web 不能仅凭现有列表可靠地区分 BMAD 技能与普通命令。
- V2 `SkillV2.list()` 从注册来源读取技能，同名时后发现的来源覆盖先前来源；但它按来源键缓存文件读取结果。`SkillV2.reload()` 目前只作用于来源 `State`，**不会清空该文件缓存**。V2 `CommandV2` 是独立的命令 Map，目前只注册配置/内置命令，没有自动技能桥接。
- V1 技能与命令都使用项目范围的 `InstanceState` 缓存。`wiscode bmad init` 在独立 CLI 进程写文件，不能直接使已运行服务里的这些缓存失效。Web 本身也缓存了命令列表。
- V2/Web 的 `session.command` 调用路径和 V2 服务端命令展开能力必须在实施时做端到端确认：当前 V2 Protocol 的命令组只提供 `command.list`。不能以“列表出现了入口”代替“点击后能执行技能”的验收。

## 方案选择

**推荐：运行时技能视图 + 按需刷新。** V1 沿用已有技能命令对象，只调整 CLI 的 BMAD 补全条件。V2 在命令服务中从当前 `SkillV2.list()` 派生 BMAD 命令视图，并按优先级与已有命令合并；列表和按名称执行必须使用同一解析规则。`/bmad-help` 别名也从当前 `bmad` 技能派生，而不是复制技能正文到固定模板。

不选择生成指针 Markdown：会引入第二套项目文件、清单所有权和清理问题，也可能与官方 skills CLI 产物及用户命令冲突。不选择在 Web 本地把任意技能伪装成命令：CLI、Web 和服务端解析会分叉，直接手输与补全选择也可能执行不同对象。

### 入口与优先级

统一按名称合并：现有配置/用户命令、内置命令、MCP 命令优先于技能派生入口；`bmad-help` 别名优先级最低。沿用 V1 当前命令冲突语义；V2 合并逻辑须显式测试插件加载顺序，不能仅凭注册顺序推断。`bmad-init` 永远保持现有命令含义。

派生命令的描述取实际发现技能的 description，进入命令列表前折叠换行和连续空白为单行并去除首尾空白，避免破坏 CLI/Web 补全排版。正文取该技能的**完整**内容，并保留技能文件所在目录信息，使相对 `scripts/`、`references/` 路径仍能解析。`/bmad-xxx <参数>` 的参数按现有命令语义传递：模板没有占位符时追加原始参数，避免丢失用户输入。不改技能权限策略；若当前 agent 禁止使用某项技能，派生斜杠入口不能成为绕过该限制的通道。V2 需在解析/执行点校验，而不只在 UI 过滤。

Web 的候选项要能标识 `source: skill` 以呈现正确的“技能”徽标；这需要评估是否扩展 V2 `CommandV2.Info`/Protocol/Client（若扩展公共协议，必须运行 `packages/client` 的 `bun run generate`）。V1 的 `source` 映射也应保留。无论是否展示徽标，执行和重名优先级均以服务端为准，客户端不自行再合并一份技能列表。

### V2/Web 执行契约

V2 必须有真正的服务端命令执行路径：按名称重新解析当前命令，把技能内容和参数展开后交给现有 V2 prompt admission/Session 流程；不得调用 V1 `SessionPrompt.loop()`，也不能只在 Web 客户端拼接字符串模拟执行。Web 继续通过同一命令提交入口调用它，保持附件、agent、model、Session ID 和错误反馈的现有语义。若现有 `session.command` 对 V2 尚未实现，应先补齐 V2 Protocol/Server/Client 的对应契约，再接 Web；这是实施门禁，不是可延期的体验优化。

命令执行时必须重新取当前技能，而非相信 Web 缓存的模板；技能已删除或权限变化时返回明确错误，不退化为普通对话文本。V2 对 `$ARGUMENTS` 与无占位符模板的处理应与 V1 一致；不能通过修改 BMAD 原文来适配。

## 初始化后刷新

成功的 `/bmad-init` 可能新增、更新或移除技能。初始化器只有在返回 `ready` 且管理清单写为 `ready` 后才公布新的项目状态；`questions`、`needs-confirmation`、`conflict`、`error` 不触发可见命令变化。跨进程同步以项目管理清单的成功状态/摘要为失效信号，不能依赖独立 CLI 进程向内存服务直接发通知，也不能只依赖短暂的文件 mtime。

指纹定义为管理清单文件的**原始字节 SHA-256**，不做 JSON 语义级重算。普通技能/命令查询先 `stat`，与内存中上次的 `(mtime, size)`（可同时记录文件标识）相同就走快速路径；元数据变化才读取文件并比较指纹。不能在每次击键或每次列表查询时读取、解析并哈希约 300 项清单。初始化成功后的显式刷新、打开 CLI/Web 斜杠候选时的主动重取，以及命令执行前的最终校验，要能强制越过元数据快速路径读取清单；原子 `rename` 不保证所有平台上 `(mtime, size)` 组合一定不同，元数据相等不能替代这些强校验点。

内容指纹变化时使 V1 的技能发现及命令 `InstanceState` 一起失效；V2 清空相应技能来源的**文件缓存**，再从新技能集合派生命令视图。刷新范围仅限对应项目/Location，不清其他项目、用户配置命令或不相关来源。缺失/损坏清单不能被当作“空技能集”静默删除用户命令；报告错误并保持安全边界。

CLI 在 `/` 补全或 `/skills` 打开时重新取得命令/技能列表。Web 在斜杠候选打开时重新取得当前目录的命令列表，至少在 `/bmad-init` 会话回到 idle 后主动失效重取；请求返回前可保留旧列表，但执行仍以服务端当前状态为准。目标是同一会话初始化成功后无需重启即可看到入口。若这条刷新链路无法通过测试，首版不得宣称“即时出现”，也不得只显示无法执行的入口；需明确降级为新开会话，并提交评审。

**实施前第一个 spike：V1 原位失效。** `InstanceState.invalidate()` 已存在，但技能服务和命令服务尚未向调用方暴露两者协同失效的路径。先在同一个已运行的 V1 服务/CLI 会话中构建“初始无 BMAD → 初始化落盘 → 失效技能发现与命令状态 → 再次 list/get/执行”的最小测试，验证 ScopedCache 能原位重建且无需重建 Layer、不会丢失 Session 状态。若不能稳定成立，先将 CLI 即时刷新降级为“新会话生效”并回到评审，不以重建整个 Layer 冒险替代。

## 测试与验收

1. 用真实 vendored BMAD 在临时项目执行 `/bmad-init`：CLI `/` 和 `/skills`、Web 两种输入组件都出现实际安装的 `bmad`/`bmad-*`；非 BMAD 技能展示不变，未安装的 Toolsmith 和已不存在的旧技能不出现。
2. CLI 手输、补全选择、`/skills` 选择与 Web 手输/补全选择均实际运行同一技能。至少用 `bmad-agent-analyst`、一个含相对资源路径的技能和带参数的命令做端到端验证；V2 验证 Session 正常入队、附件和 agent/model 不丢失。
3. 配置命令、MCP 命令和 `bmad-init` 与同名技能冲突时，列表只出现优先项，CLI/Web/服务端执行结果一致。`bmad-help` 仅在 `bmad` 存在且无同名用户命令/技能时可用，其展开正文与 `/bmad` 相同。
4. 在已打开的 CLI 和 Web 会话中初始化、重跑更新、退役技能，下一次打开补全即反映变化；另一个项目的命令不变。失败或待确认状态不误触发刷新。验证同名项目技能覆盖全局技能后的命令内容来自项目副本。覆盖相同 `(mtime, size)` 但不同内容的清单替换，以及普通查询的 `stat` 快速路径与主动刷新强校验。
5. 测试 V2 缓存中先有空目录、随后落盘技能的场景；单纯 `State.reload()` 不清文件缓存的回归必须被覆盖。权限拒绝、文件删除后的旧 Web 列表执行应返回错误，而非绕过权限或发成普通文本。
6. 在相关 package 目录运行聚焦测试和 `bun typecheck`；若变更 V2 Protocol/Server `HttpApi`，从 `packages/client` 执行 `bun run generate`，不手改生成文件。最终在 macOS 桌面与独立 CLI 冒烟，Windows 实机验证按原 BMAD 集成验收计划执行。实施后先交付人工验证，不自行提交。

## 评审重点

请重点确认两项产品语义：其一，BMAD 技能入口是“发现才显示”，因此上游删掉的旧命令不会永久保留；其二，`/bmad-help` 是兼容别名而非独立技能，优先级低于用户自定义命令。技术门禁是 V2 真正的命令执行与跨进程缓存刷新，不能只验收菜单截图。
